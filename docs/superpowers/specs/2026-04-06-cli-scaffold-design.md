# M1: CLI Scaffold — Design Spec

> Approved design for `@tourguide/cli` and foundation fixes in `@tourguide/core`.
> Parent milestone: [M1 in roadmap](../../roadmap.md)

---

## Scope

This milestone delivers three things:

1. **`@tourguide/cli`** — a new package with `validate`, `play`, and `summary` commands
2. **`buildGraph` fix** — merge per-step connections into the unified graph
3. **Traversal hardening** — gracefully handle empty chapters and empty tours

## Architecture: Thin CLI Wrappers

The CLI is a thin composition layer over `@tourguide/format` and `@tourguide/core`. There are no heavy abstractions — commands call core APIs directly, and rendering is handled by pure formatting functions that take data and return strings.

```
packages/cli/
├── package.json
├── tsconfig.json
├── src/
│   ├── cli.ts              # Commander setup, registers commands
│   ├── commands/

│   │   ├── play.ts
│   │   └── summary.ts
│   └── format/
│       ├── errors.ts       # Validation errors → styled strings
│       ├── tour.ts         # Step/chapter/summary → styled strings
│       └── code.ts         # Source code snippet → styled string with line numbers
├── tests/
│   ├── validate.test.ts
│   ├── play.test.ts
│   ├── summary.test.ts
│   └── format/
│       ├── errors.test.ts

```

## Global CLI Behavior

- **`--version`**: prints the package version (read from `package.json` via an import or injected at build time). Configured via `program.version()` in commander.
- **`--help`**: auto-generated by commander for the program and each subcommand.
- **Exit codes**: 0 on success, 1 on validation failure, file errors, or invalid usage.

## Commands

### `tourguide validate <file...>`

1. Read each file (exit 1 with error message if not found or unreadable)
2. Call `loadTour(filePath)` from `@tourguide/core` — catches `TourLoadError` on failure
3. On success: `✓ valid — Tour Title (3 chapters, 12 steps)`
4. On failure: iterate `TourLoadError.errors` and format each using the `code` field to distinguish error types:
   - Schema errors (Zod codes like `invalid_type`, `invalid_union`): show path and message (e.g., `error: steps[2].range.start.line — Expected number, received string`)
   - Semantic errors (custom codes like `unknown-chapter-reference`): show description (e.g., `error: Step "setup-db" references unknown chapter "nonexistent"`)
   - Load errors (`invalid-json`, `file-read-error`): show the underlying message
5. Accepts multiple files — validates each, reports per-file, exits 1 if any fail
6. Exit codes: 0 all valid, 1 any invalid or file error

### `tourguide summary <file>`

1. Load and validate the tour (exit 1 on error)
2. Print formatted summary:
   - Tour title and description
   - Mode (diff/codebase) with refs if applicable
   - Overview summary text
   - Chapter list: title, step count, one-line summary per chapter
   - File map: file path, relevance level (color-coded: primary=bright, secondary=dim, context=dimmer), description
3. Pure output, pipe-friendly, no interactivity

### `tourguide play <file>`

1. Load and validate the tour
2. Call `firstPosition(tour)` — if it returns `null` (empty tour), print "Tour has no steps" and exit 0
3. Print header: tour title, description, "Press Enter to advance, q to quit"
4. Show the first step
5. Input: Enter (or right arrow) advances via `nextStep()`, `q` quits
6. On chapter boundary: show a chapter transition separator
7. At end of tour: print "Tour complete" with total steps visited
8. On `q`: print progress summary and exit cleanly

**Step display** (steps separated by `───────` horizontal rules):

```
  Chapter 2/4: Data Validation
  Step 3/12 — Validate Input Schema

  src/validation/schema.ts:15-42

  ┌─────────────────────────────────
  │ 15  export function validateSchema(input: unknown) {
  │ 16    const result = schema.safeParse(input);
  │ 17    if (!result.success) {
  │ 18      throw new ValidationError(result.error);
  │ 19    }
  │ 20    return result.data;
  │ 21  }
  └─────────────────────────────────

  This function is the entry point for all input validation.
  It uses Zod's safeParse to validate against the schema
  defined above, converting parse failures into domain errors.
```

- Chapter/step progress in dim color at top
- File path and range on its own line
- Source code in a bordered box with line numbers — shown by default, gracefully omitted if source files aren't accessible
- Step description below the code

**Chapter transition** — more prominent separator:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Chapter 3: Error Handling
  Building resilient error boundaries
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**stdin handling:** `process.stdin` in raw mode, listen for keypress events. Enter/right-arrow advances, `q` quits. No other keys do anything.

## Foundation Fixes (in `@tourguide/core`)

### `buildGraph` — merge per-step connections

Currently only indexes `tour.connections` (top-level array). Steps also have `connections` arrays that the format schema supports.

**Fix:**
1. Iterate all chapters → steps → `step.connections`, collect alongside `tour.connections`
2. Deduplicate: same `from` + `to` + `type` = one edge. Top-level version wins if descriptions differ.
3. Build adjacency index from merged, deduplicated set

Public API unchanged: `buildGraph(tour): TourGraph`.

### Traversal — handle empty chapters and empty tours

**Changes:**
- `firstPosition(tour)` → returns `null` if no chapters or first chapter has no steps
- `lastPosition(tour)` → returns `null` for empty tour
- `nextStep` / `prevStep` → skip empty chapters, return `null` if no more non-empty chapters
- `nextChapter` / `prevChapter` → skip empty chapters
- `getProgress` → handle null position (0/0 progress)

Return types change from `TourPosition` to `TourPosition | null`. Callers need null checks.

## Testing Strategy

### CLI command tests (`packages/cli/tests/`)

Commands are testable as functions that take a file path and a writable stream (defaulting to `process.stdout`). Tests pass a buffer to capture output.

**`validate.test.ts`:**
- Valid file → exit 0, output contains checkmark and tour title
- Invalid file (schema errors) → exit 1, output contains error paths
- Invalid file (semantic errors) → exit 1, describes dangling references
- Nonexistent file → exit 1, file-not-found message
- Multiple files, mix of valid/invalid → exit 1, per-file reporting

**`summary.test.ts`:**
- Valid tour → output contains title, mode, chapter names, step counts, file map entries
- File map entries show relevance levels

**`play.test.ts`:**
- Test rendering functions in isolation: given a `TourPosition`, produces correct output string
- Test step-advance logic: given a position, `nextStep` produces expected next position
- Interactive stdin not tested directly — tested through the rendering and traversal layers

### Format function tests (`packages/cli/tests/format/`)

- `errors.test.ts`: schema error formatting, semantic error formatting, file error formatting
- `tour.test.ts`: step rendering (with/without code), chapter transition, summary layout, progress display

### Foundation fix tests (in `packages/core/tests/`)

- `graph.test.ts`: per-step connection merging, deduplication, partial merge
- `traversal.test.ts`: empty chapters, empty tours, null returns, skip-over behavior

### Fixtures

Reuse existing: `packages/core/tests/fixtures/*.tourguide` and `examples/sample.tourguide`. New fixture for empty-chapter edge case added to `packages/core/tests/fixtures/`.
